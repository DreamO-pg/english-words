## Аудит

### Методика

Из AUDIT.md (дата 2026-11-10, коммит `3775165`, ветка `docs/audit`):
- **Только чтение кода**: код в ходе аудита не менялся, сервер и боевой токен не использовались.
- Разобраны архитектура и пользовательские сценарии, затем пройден чек-лист «бот + бэкенд + Mini App». Пункты, неприменимые к проекту (команды бота, `callback_data`, `initData`, CORS, секреты на сервере, бэкапы БД), выписаны отдельно с объяснением (AUDIT.md, 2.1).
- Запущены `tsc --noEmit`, `npm run build`, `check:words`, `check:engine`, `npm audit`. Отдельный скрипт вне репозитория искал коллизии вариантов ответа, совпадения `ru[0]` и МФА с `r` на конце.
- Шкала серьёзности: **К** — критично, **В** — высокая, **С** — средняя, **Н** — низкая. Трудоёмкость: **S** — до часа, **M** — до дня, **L** — больше дня.
- Исправления шли пятью этапами (данные → логика → контент → Telegram и UX → эксплуатация), каждый отдельным коммитом и с проверкой в браузере и на моке `Telegram.WebApp`.
- Ограничение аудита: **настоящие клиенты Telegram на iOS, Android и Desktop не проверялись**, всё про SDK проверено на моке.

### Топ-3 риска на момент аудита

1. D-01 — сбой чтения CloudStorage ведёт к безвозвратной перезаписи прогресса.
2. L-02 — в 16 карточках среди «неправильных» вариантов стоял правильный.
3. L-01 — уровни A1, A2, C1 в интерфейсе без слов.

### Остаточные ограничения после аудита

Из AUDIT.md, «Итог по аудиту»:
- `stats` и `settings` между устройствами: «последняя запись побеждает».
- Слово, удалённое на одном устройстве, может вернуться записью прогресса с другого, если там оно ещё в очереди.
- Урок, прерванный на середине, не сохраняется (смягчено подтверждением, T-02).
- Словарь вычитан не носителем.
- SDK проверен на моке, а не на живых клиентах.
